# Format exact des dates Prisma 5.22 / SQLite — preuve littérale (Phase 0)

Mesuré le 2026-11-09 dans `server/` sur une base SQLite jetable (`DATABASE_URL=file:./tmp-probe.db`),
après `corepack pnpm exec prisma migrate deploy` (12 migrations), avec le client Prisma généré 5.22.0.
Node v24.12.0, Windows x64. Scripts jetables `server/.probe-dates.ts`, `.probe-dates2.ts`, `.probe-dates3.ts`
(supprimés après usage). Logs complets : `%TEMP%\lc-audit\probe-dates-paris.log`, `probe-dates-utc.log`,
`probe-dates2.log`, `probe-dates3.log`.

## CONCLUSION (à retenir)

- Prisma + SQLite stocke `DateTime` en **INTEGER 64 bits = millisecondes Unix epoch, UTC**.
- `typeof(colonne)` en SQL brut = **`integer`** ; pas de texte, pas de REAL, pas de fuseau stocké.
- Précision = **milliseconde** ; toute fraction sous-ms est tronquée.
- Indépendant de `TZ`/du fuseau système : aucune conversion locale au stockage ni à la lecture.
- Le client Prisma relit ces entiers en `Date` JS et `toISOString()` restitue `"2024-01-02T03:04:05.678Z"`.
- Piège : le défaut SQL `CURRENT_TIMESTAMP` (si un INSERT brut omet la colonne) écrit du **TEXT**
  `"YYYY-MM-DD HH:MM:SS"` en UTC à la **seconde** ; Prisma le relit quand même (interprété UTC).
- Parseur Prisma : accepte INTEGER ms, TEXT `"YYYY-MM-DD HH:MM:SS"`, ISO 8601 avec `Z` ou offset ;
  rejette `T` sans timezone, espace+fraction, REAL fractionnaire (voir probe 3).

- INSERT brut **sans** `createdAt` → défaut SQL `CURRENT_TIMESTAMP` → stockage **text** `"2026-11-09 21:49:42"` (UTC, seconde), relu par Prisma `"2026-11-09T21:49:42.000Z"`.
- INSERT brut avec `'2025-01-02 03:04:05'` → text, relu `"2025-01-02T03:04:05.000Z"` (heure interprétée **UTC**).
- Un INSERT via Prisma dans la même table écrit bien `integer` ms.

```

storage[iso_no_tz] {"t":"text","cast_text":"2026-11-09T21:49:42.123","h":"323032362D31312D30395432313A34393A34322E313233"}
client_read[iso_no_tz] ERREUR: PrismaClientKnownRequestError: Inconsistent column data: Conversion failed: input contains invalid characters
storage[iso_offset] {"t":"text","cast_text":"2026-11-09T21:49:42.123+02:00","h":"323032362D31312D30395432313A34393A34322E3132332B30323A3030"}
client_read[iso_offset].createdAt = "2026-11-09T19:49:42.123Z" (typeof=string)

client_read[space_utc].createdAt = "2026-11-09T21:49:42.000Z" (typeof=string)
storage[space_frac] {"t":"text","cast_text":"2026-11-09 21:49:42.987","h":"323032362D31312D30392032313A34393A34322E393837"}
client_read[space_frac] ERREUR: PrismaClientKnownRequestError: Inconsistent column data: Conversion failed: input contains invalid characters
storage[real_frac] {"t":"real","cast_text":"1704164645678.9"}
client_read[real_frac] ERREUR: PrismaClientKnownRequestError: Inconsistent column data: Could not convert value 1704164645678.9011 of the field `lastAccessedAt` to type `DateTime`.
```

Synthèse du parseur (comportement observé, Prisma 5.22) :

| Valeur en base `DATETIME` | Stockage | Relu par Prisma |
|---|---|---|
| `1704164645678` (int ms) | integer | `2024-01-02T03:04:05.678Z` ✅ |
| `2026-11-09 21:49:42` | text | `2026-11-09T21:49:42.000Z` (UTC) ✅ |
| `2026-11-09T21:49:42.123Z` | text | `2026-11-09T21:49:42.123Z` ✅ |
| `2026-11-09T21:49:42.123+02:00` | text | `2026-11-09T19:49:42.123Z` (offset respecté) ✅ |
| `2026-11-09T21:49:42.123` (T sans TZ) | text | ❌ `Conversion failed: input contains invalid characters` |
| `2026-11-09 21:49:42.987` (espace + fraction) | text | ❌ idem |
| `1704164645678.9011` (REAL) | real | ❌ `Could not convert value … to type DateTime` |

**Effet de bord important** : une seule valeur non convertible dans une colonne `DATETIME` fait échouer
**toute requête qui sélectionne cette colonne**, y compris un simple `SELECT … ORDER BY` → `P2010 Raw query failed`
(constaté en fin de probe 3). Le migrateur Rust doit donc tolérer/parsing défensif ou normaliser la base.

## Implications Rust (résumé ; détail dans audit-dynamique.md §7)

- Lire/écrire les colonnes datetime en **i64 millisecondes epoch UTC** (`chrono::DateTime<Utc>::from_timestamp_millis`).
- Écrire `now()` en ms côté application, **jamais** via `DEFAULT CURRENT_TIMESTAMP` (seconde + TEXT).
- Parseur d'entrée tolérant : i64 → text `YYYY-MM-DD HH:MM:SS` (UTC) → RFC 3339 `Z`/offset ; rejet explicite sinon.
- API : sérialiser en ISO 8601 UTC avec millisecondes + `Z` pour rester compatible avec `Date.toISOString()` du legacy
  (protocole `overlay-protocol` v1.2.0, extension/overlay TS).
